# Лабораторна робота №3 — Графова база даних Neo4j (MovieLens 1M)

## Схема графа

```text
+-----------------------------------+                     +-----------------------------------+
|            (:User)                |                     |            (:Movie)               |
+-----------------------------------+                     +-----------------------------------+
| userId (Integer, ID)              |                     | movieId (Integer, ID)             |
| gender (String)                   | ----[:RATED]------> | title (String)                    |
| age (Integer)                     |  rating (Integer)   | genres (String, pipe-separated)   |
| occupation (Integer)              |  timestamp (Int)    |                                   |
+-----------------------------------+                     +-----------------------------------+
```

---

## Частина 1 — Проєктування схеми

1. **Які сутності стали вузлами, а які — ребрами? Чому?**  
   Вузлами стали сутності **User** і **Movie**, оскільки це ключові об'єкти предметної області з власними атрибутами (`userId`, `gender`, `age`, `occupation` та `movieId`, `title`, `genres`). Ребром зроблено **RATED**, оскільки оцінка описує спрямовану взаємодію між конкретним користувачем і фільмом у певний момент часу (`rating`, `timestamp`).

2. **Оцінка користувача за фільм — ребро `(User)-[:RATED]->(Movie)` чи окремий вузол `(Rating)`?**  
   Для базової задачі вигідніше ребро `[:RATED]`: воно компактніше, зменшує кількість проміжних хопів при обходах графа (наприклад, при пошуку спільних фільмів або рекомендаціях) і природно виражає подію оцінювання. Окремий вузол `(:Rating)` виправданий лише тоді, коли сама оцінка має складну власну структуру (наприклад, текстовий відгук, модерацію, теги, кілька критеріїв або історію редагувань).

3. **Чому жанри фільму вигідніше зберігати як окремі вузли `(Genre)`, а не як список/рядок у властивості `Movie`?**  
   Окремі вузли `(:Genre)` зі зв'язком `(:Movie)-[:HAS_GENRE]->(:Genre)` дозволяють швидко знаходити всі фільми жанру без сканування властивостей і строкових операцій (`CONTAINS` / `split`), будувати рекомендації за жанровими вподобаннями та аналізувати графову топологію жанрів. У поточній реалізації в AuraDB використано властивість `genres` для швидкого імпорту без зайвих зв'язків, але для аналітики жанрів модель з окремим вузлом гнучкіша.

## Частина 2 — Завантаження даних

- Дані з MovieLens 1M конвертовано з кодування `Latin-1` і роздільника `::` у CSV (`UTF-8`, роздільник `,`). Через обмеження безкоштовного інстансу AuraDB завантажено `200 000` записів оцінок, `6 040` користувачів та `3 883` фільми.
- Використання `MERGE` гарантує ідемпотентність (відсутність дублікатів при повторному запуску).
- Індекси за `userId` та `movieId` пришвидшують пошук вузлів під час створення ребер.
- `apoc.periodic.iterate` з `parallel: false` розбиває завантаження на батчі, щоб уникнути переповнення пам'яті або таймаутів транзакцій та запобігти гонкам при записі.

### Відповіді на запитання
1. **Що означає довжина шляху в даному контексті?**  
   Довжина шляху (`length(path)`) — це кількість ребер `[:RATED]` між початковим і кінцевим вузлами в ланцюжку обходу.
2. **Один хоп — це один крок по ребру `RATED`, а шлях довжини 2 означає, що два користувачі оцінили один і той самий фільм.**  
   Так: `User A -[:RATED]-> Movie X <-[:RATED]- User B` має 2 ребра, тобто довжину 2 (наприклад, `User 1` і `User 10` з'єднані через `Toy Story (1995)`).
3. **Як інтерпретувати шлях довжини 4? Довжини 6?**  
   - **Довжина 4** (`User1 -> Movie1 <- User2 -> Movie2 <- User3`): користувачі не мають спільного високо оціненого фільму напряму, але пов'язані через проміжного користувача та два фільми.
   - **Довжина 6** (`User1 -> Movie1 <- User2 -> Movie2 <- User3 -> Movie3 <- User4`): ще довший ланцюжок опосередкованої схожості/перетину аудиторії через трьох проміжних користувачів і три фільми.

2. **Чому запит, що зачіпає такий вузол, працює повільніше, ніж запит по «звичайному» вузлу з тими самими індексами?**  
   Індекс швидко знаходить сам вузол за ID, але далі рушію графа доводиться обійти значно більше сусідніх ребер і проміжних шляхів (комбінаторне зростання при багатоходових обходах типу `MATCH (u1)-[:RATED*]-()-[:RATED*]-(u2)`).

   Якщо винести жанри в окремі вузли `(:Genre)`, вони стануть класичними супервузлами (тисячі фільмів на кожен популярний жанр). Для боротьби з цим варто фільтрувати за додатковими умовами/вагами до розширення шляху, обмежувати глибину пошуку, виносити агрегати/ваги зв'язків або розбивати/фільтрувати за рейтингом (`rating >= 4`) ще на ранніх етапах запиту.

## Частина 6 — Аналіз і висновки

1. **Граф vs SQL.**  
   У реляційній базі базові агрегації та фільтрації (Запити 1, 2, 4) пишуться просто через `JOIN`, `GROUP BY` і `HAVING`, але багатоходові зв'язки та пошук найкоротшого шляху (Запит 6) у стандартному SQL вимагають або жорстко заданої кількості самоз'єднань (`JOIN` таблиці оцінок самої на себе), або рекурсивних CTE (`WITH RECURSIVE`), які стають громіздкими й менш наочними при довільній довжині шляху та контролі циклів. У Cypher шлях задається декларативно (`shortestPath`).

2. **Де граф програє?**  
   Реляційна модель часто зручніша та ефективніша для суцільних аналітичних агрегацій по всій таблиці (наприклад, масові фінансові/статистичні звіти, групові метрики по всіх користувачах без прив'язки до топології, пакетний ETL та експорт плоских таблиць).

3. **Покращення схеми.**  
   - Для **Запиту 1** та **Запиту 4** винесення жанрів у вузли `(:Genre)` і попереднє обчислення або індексування властивостей/агрегатів (або створення індексу за `m.title`) прискорить відбір і групування жанрів.
   - Для **Запиту 5** та **Запиту 6** фільтрація ребер за високим рейтингом (`rating >= 4`) або матеріалізація зважених зв'язків схожості між користувачами суттєво зменшує кількість проміжних гілок під час обходу графа.
